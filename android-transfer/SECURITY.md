# Native Transfer security and Android 17 plan

## Non-negotiable boundaries
The native app ID `dev.expository.transfer`, AndroidKeyStore encrypted one-shot storage with explicit SFTP **connection-only bookmark** UI (#234, no passwords, biometrics or automatic restoration), OAuth client (not configured) and limited user-initiated SFTP `INTERNET` permission are independent of Expository's read-only GitHub Pages explorer. Never use or copy the web app's GitHub token. The G0 synthetic shell originally had no network access. The G4 PR #37 adds standard `INTERNET` for an explicitly user-configured SSH host, with mandatory pinned SHA-256 fingerprint, no LAN target-37 entitlement claim, no account/broad-file permission and no credentials or file bytes persisted in source or telemetry. The G2 picker-initiated Local→Local Copy path can create a **user-chosen SAF destination document** and write bytes to it, without INTERNET, remote credentials, broad storage permissions, or source deletion. It is foreground-only. PR #42 commits a private AtomicFile write-ahead record before transfer streams, flags interrupted attempts as uncertain, and displays a review count; it cannot yet automatically resume or reconcile destination state.

G4 SFTP credentials are entered by the user and retained only for a short-lived in-memory authenticated session; although an AndroidKeyStore encrypted-record primitive exists (#182, E2), **only explicitly consented, encrypted connection-coordinate bookmarks without passwords are implemented** (#234). Actual remote login/secret persistence, unattended reconnection, biometric enforcement and post-process restoration are not implemented. Credentials are never placed in drag payloads, scripts, receipts, GitHub Secrets or CI artifacts. Redact authority names, paths and user filenames in telemetry; the current deterministic CI uses synthetic names only. GitHub Actions debug signing is test-only; never publish its debug keystore or present the APK as a signed release.

## Optional app-session authentication gate (policy only, not yet enforced)

The owner requires configurable extra credentials to view/interact with local transfers (once per app session by default **when enabled**, with more/less secure cadences), and platform fingerprint/biometric or device-credential authentication for protected local/remote sessions. The initial pure `SessionAccessGate` implementation has no Android authenticator or protected UI yet: **never claim an enabled biometric lock, saved password or auto-unlocked session from these scenarios**. Grant proof must come only from a native BiometricPrompt/device-credential success, and may not replace SSH/FTPS authentication or an Android SAF grant. Per-connection remote identities must remain independent. See [session authentication contract](../docs/android-transfer/SESSION-AUTHENTICATION.md) for API-version constraints, E2/E4 gates and vault requirements.

## Android 17 LAN rule, API 37
Android 17 enforces `android.permission.ACCESS_LOCAL_NETWORK` for targetSdk **37+**, including socket connections to LAN FTP/SFTP servers. The G0 skeleton targets SDK 36 and **must not claim** that it has tested local-network access or request the new Android 17 permission at this target level. When moving the current target 36 app to target 37, request `INTERNET` for internet hosts; add and request `ACCESS_LOCAL_NETWORK` at runtime **only when needed for a user-initiated LAN connection**. Provide a plain explanation, denial/revocation handling and deterministic fake verification. Never silently downgrade to plaintext FTP or retry indefinitely after a permission denial. Follow the official platform guidance: https://developer.android.com/privacy-and-security/local-network-permission .

## Provider and destructive semantics
The Android Storage Access Framework picker returns opaque granted URIs; never manufacture filesystem paths or escalate to MANAGE_EXTERNAL_STORAGE. Persist grants only if the provider legally offers them; revoke/URI-remap stops or revalidates jobs. Remote-to-Drive copy must use verified writable SAF access or a narrowly authorized Drive API adapter; Share and external Docs opening remain unverified handoffs. Drive conversion is a separate opt-in fidelity-changing action. No source delete before destination proof and explicit confirmation.

## Single-document picker execution boundary

G2 only accepts `content://` URIs returned from user-initiated `ACTION_OPEN_DOCUMENT` and `ACTION_CREATE_DOCUMENT`. Android guarantees that the second action creates a new document (it may alter the displayed name), so the planner has a separate `SAF_NEW_DOCUMENT_PICKER` witness rather than fabricating a complete parent listing. This mode is restricted to one file, Copy, and a granted Local SAF destination. The app never uses `ACTION_OPEN_DOCUMENT` to target an existing file for output. Provider content URIs remain in memory only. Android inbound ACTION_SEND_MULTIPLE uses at most 12 distinct, read-granted content URIs with strict ClipData/EXTRA_STREAM agreement; receiving a batch never auto-uploads, and each chosen remote SFTP write is independently preflighted, journaled and verified. API 35 no-silent-upload UI is E2 only, not server delivery. The ContentResolver `w` mode may be provider-specific; because this target is newly created there is no intent to overwrite an older user document. On write failure, a partial/empty created document may remain; automatic deletion is intentionally out of scope. Read-back digest match proves bytes returned by that provider, not eventual Google Drive cloud synchronization. **An app-private attempt journal exists, but there is no resumable queue, automatic remote reconciliation or source delete.**

## Non-destructive remote directory creation

The G6 New Folder operation in PR #46 commits a private attempt journal and revalidates an immutable complete sibling snapshot before direct SFTP MKDIR. It verifies the resulting directory with an authenticated server stat. No synthetic test or command ACK alone warrants an Android/device completion claim. An ambiguous reply leaves an uncertain folder that must be inspected manually before retry; the app never recursively deletes existing remote content as cleanup. Folder operations with more than 200 visible children currently fail closed until proper pagination exists.

## Native same-server Move policy

PR #47 introduces explicit one-file Move between distinct folders of the *same* pinned-SFTP session. A direct SFTP rename is permitted only for a validated immutable `VERIFIED_REMOTE_RENAME` plan, complete collision-free destination listing and matching authenticated namespace. Neither the Android device nor client relays file bytes, and no separate source Delete command is used. An attempted mutation is journaled before the request. A successful reply is insufficient without observed original-name absence and destination metadata agreement. The synthetic fixture tested no-overwrite behavior, but other servers, concurrent writers and lost replies remain unverified; user-facing receipt must distinguish observed metadata from content hashes, and never retry automatically.

## Evidence
Synthetic fixture data are **E1**, an APK compilation artifact is **build provenance**, not a device acceptance. Keep debug APK artifacts at short retention; no user data in screenshot jobs. Real device, server and OAuth tests must be opt-in with separately documented consent and scope.

## Future cloud and GitHub endpoint security (2026-10-27)

Follow [universal locations](../docs/android-transfer/UNIVERSAL-LOCATIONS.md) before building cloud/repository adapters. Android DocumentsUI URI grants, Drive OAuth account scopes and GitHub auth tokens are **three distinct authorities**; never infer one from another, reuse the web explorer token, or silently escalate permissions. Only persist eligible Android URI grants; validate live capability before each mutation, support revocation/account switch, keep auth material in protected device-local storage, and exclude secrets/private paths/file content from logs and drag payloads. Branch HEAD/revision pinning, changed-tree rejection and post-commit reconciliation are required for GitHub writes; no blind retries. Scope addition is not security acceptance.
