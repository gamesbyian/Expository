## Diagnosis: preserve the good foundations, close the integration gap

The Kotlin core/planner already contains opaque location/item identity, three-state capability proof, immutable Copy/Move plans, and independent workspace pane state. Core/engine has foreground verified Copy, an explicit uncertainty state, per-attempt journaling, a recursive folder engine and a bounded synthetic batch coordinator. SAF has genuine scoped DocumentsProvider browsing, file and recursive tree copying with staged checks and SHA-256 readback. SFTP has pinned authenticated browsing and selected Copy/Move paths; FTPS has TLS-verified browsing and guarded Save As; insecure FTP is opt-in read-only. Single and Dual layouts are real, but Single remote actions and the operation matrix are incomplete.

The integration debt is now more important than another isolated helper: TransferActivity.kt is roughly 1,250 lines, SftpBrowseCard.kt roughly 2,000 lines, and endpoint-specific cards still own operation orchestration and picker/review lifecycle. There is a risk of implementing each source/destination pairing again in different UI cards, with divergent safety checks, progress and receipts. Do **not** discard the existing accepted code or perform a big-bang Compose refactor. Extract one tested vertical seam at a time, preserving the app's working flows.

The other bottleneck is **proof, not just implementation**. Open PR #292 attempts real OS-picked source and destination trees using a separate synthetic DocumentsProvider APK. The latest exact-head Android E2 run [#41002248669](https://github.com/gamesbyian/Expository/actions/runs/41002248669) failed at SYSTEM_DESTINATION_PICKER_NOT_FOREGROUND_COPY_PROPOSAL_REJECTED_OR_ACTIVITY_MISSING, before byte acceptance. Its APK compile succeeded; it **must remain unmerged** until the actual two-grant Copy is observed and independently read back. There is no verified Google account, physical handset, complete process-death recovery or signed release.

This is a **partial order**. Finish independently valuable items when another lane lacks a device, test account or external endpoint. Do not make all work wait for E4; equally, do not treat E1/E2 fixtures as a substitute for E4.

## Architecture decisions for the next implementation PRs

1. **Extract a common command boundary without changing behavior.** Define a presentation-independent SelectedSource, DestinationChoice, ActionIntent (Copy, explicit Move, New Folder, Rename, Save original, handoff), ApprovalSnapshot and OperationOutcome in Kotlin. Identity includes endpoint/account/profile/session, scoped tree/root and generation, current container, opaque child ID and observed revision where available. An item name or breadcrumb is never authorization. The reducer invalidates approvals on navigation, swaps, provider grant changes, share events and reconnection. Both Single and Dual submit identical intents. Unit-test equivalent plan digest and identical block/review behavior before moving a second route.
2. **Adapter capability contracts are narrower than a filesystem interface.** Supply typed paged List, Stat, Read, CreateChildNoReplace or explicitly Unsupported, destination readback, and conditional Rename/Move/Delete; attach authority identity, capability evidence/expiry, completeness, case/Unicode rule and revision proof. Keep path-only FTP identity explicitly weak. Do not invent atomic rename, seek, permanent grants, provider-managed Move, same-server Copy or whole-account Drive access. Provider-specific implementation stays outside Compose; no Android ContentResolver or remote SDK object in core/planner.
3. **Move UI side effects behind the shared dispatcher incrementally.** Start with one already-proven SAF file Copy, then SAF recursive Copy, then SFTP upload/download/relay; test each unchanged journey against a known baseline. The large TransferActivity and SftpBrowseCard are refactoring targets, **not** an instruction to rearrange thousands of lines before functional tests. Keep source selection, review, execution, result display and progress separate; use a consistent immutable request token rather than screen-specific mutable flags as authority.
4. **Durable Copy lifecycle.** Define a stable non-secret attempt ID and journal states CREATED → REVIEWED → ATTEMPT_RECORDED → WRITE_ACKNOWLEDGED → DESTINATION_CONFIRMED → CONTENT_HASH_VERIFIED, plus BLOCKED, STOPPED_PARTIAL and UNCERTAIN as appropriate. Journal before each potentially mutating step, including folder creates, server-side renames and future deletion. If provider creation/commit/readback response is ambiguous, stop, show review-required state and reconcile observed destination identity rather than blindly resending. A progress counter increments only after committed verified steps. Sensitive names and credentials must not leak into shared logs, telemetry or CI artifacts; private device journals need access controls and retention policy.
5. **Foreground first; scheduled execution only with proper authorization.** Prove cancellation and interruption in the existing verified foreground path, then persistence, app process death, grant expiry, offline reconnect, device restart and operator-driven reconcile. Background WorkManager/foreground-service integration must obey modern Android execution and notification constraints; it must never auto-retry an uncertain write. Do not cache long-lived network credentials or persist ephemeral picker grants by assumption. An opted-in saved profile and optional biometric gate require separate security proof.
6. **Mutation and Move safety.** Copy always retains source. Same-authority Move may use verified no-replace provider/server primitives only after fresh complete membership and unchanged identities. Cross-authority Move is independently verified Copy followed by a *separate* authorized source deletion; a handoff/acknowledgement is insufficient. Same-authority SAF recursive Copy stays blocked until disjoint ancestry is proved. Never use FTP RNFR/RNTO to implement Copy, or generic FTPS STOR when overwrite behavior is unproven.
7. **Provider expansion through adapters, not new app variants.** First generic Android SAF and pinned SFTP, then trusted FTPS write paths, then real Drive chosen-parent access. Public GitHub remains read-only except separately approved branch/commit publishing, outside the web explorer. In Drive, use a proven user-scoped SAF destination or explicitly authorized least-privilege drive.file/API uploader; distinguish selected existing parent, app-owned folder, one-file Save As, unverified Sharesheet handoff and native Docs conversion. Test account grant and parent write feasibility before building the full browse UI.
8. **UI should communicate the same truth as the engine.** Permanent default Single is a full-featured location browser; optional Dual is independently navigable Local/Local, Local/Remote or Remote/Remote, with A/B collapse on phone. Show source, destination, capability, conflicts, potential network relay, progress, uncertain/partial states and exact receipt tier. Drag proposes the same Copy plan as the accessible button and never writes on drop alone. Preserve 44dp targets, 360/393/412dp and 200% type, keyboard/TalkBack and state restoration. Focus polishing on genuine workflows after command parity, not before.

## Route implementation ladder (repeatable vertical-slice acceptance)

Each new source→destination direction must pass the same checklist:

1. **Read-only observation:** genuine source enumeration and destination identity/grant with a complete, fresh mutation-authorizing listing or narrowly scoped new-document grant. Positive and revoked/stale/ambiguous negative fixtures.
2. **Immutable review:** actual selected items, folder hierarchy and destination, byte count where known, accurate Copy versus Move semantics, explicit confirmation and invariant digest shared by Single/Dual/drag.
3. **Mutation safety:** fresh revalidation, exclusive/no-replace destination creation, write-ahead attempt, bounded streaming, cancellation after each failure phase, identity/ancestry rechecks and no source deletion for Copy.
4. **Proof:** source retention, actual bytes streamed, readback SHA-256 where supported, destination membership check after readback, individual committed receipts. Only supported proof tiers can be displayed.
5. **Recovery:** simulate lost reply, timeout, process death and provider mutation; UNCERTAIN stops batch; manual inspect/reconcile without duplicate file or destructive cleanup.
6. **UX/interop:** run scoped E1, Android API35 real-picker E2 when relevant, controlled server E3 and explicitly approved external/physical E4 when available. Mark skipped or unavailable gates as open. A successful compile is never an E2 transport pass.

Small safe slices should end in one exact-head testable PR, not several stacked branches fighting for a shared Compose file.

## Ranked execution frontier and concurrency rules

**First unblocked path:** (1) diagnose #292's missing destination-picker launch/observation at the exact test head; do not weaken assertions or manually grant the fixture's content URIs; (2) extract one shared immutable UI request/dispatcher around an already proven SAF Copy; (3) add Android operator-driven journal read/reconcile semantics with a no-auto-retry rule; (4) re-run real two-authority OS-picked folder Copy and then extend to SFTP/FTPS through that boundary. These are small independently mergeable steps, not a requirement to delay all others.

**Parallel isolated lanes:** secure protocol/FTPS interop and mutation capability (adapter-only + controlled server tests), Drive scoped-authority feasibility (design/tests before broad UI), renamer no-replace/collision fixtures and a 10k-row virtualization prototype, session-gate/Keystore threat review, responsive/a11y tests, and source-neutral regression fixtures. Coordinate ownership before editing TransferActivity, SftpBrowseCard or shared navigation/state files. Independent read-only investigations can advance while endpoint/server approval is unavailable.

**Scope discipline:** No web Pages mutation in Android PRs; no refactor justified only by line count; no simultaneous ownership of shared files; no production tokens or private server identity in test evidence. Do not force-merge a red PR, let a stale PR silently rebase over another worker or run live external writes without documented disposable authorization.

## Definition of done and stop-ship boundaries

The product requires P01–P12, not merely green modules: secure FTP/FTPS/SFTP, scoped multi-file/folder transfers, both Single and Dual UX, all authorized route directions, safe New Folder/Move/rename Apply/undo, recoverable queue, verified original-to-Drive and distinct Docs actions, device-local security, accessibility and independently signed beta. The old G0–G9 labels in the release ledger continue to track evidence, never infer completion by calendar phase.

- **E1** pure planner/engine/fault tests; **E2** Android emulator with actual ContentResolver/system UI; **E3** controlled authenticated server bytes and interop; **E4** authorized third-party cloud/physical device; **E5** separately reviewed signed release. Always name exact code SHA, job, assertion, provider/transport and limit.
- Stop ship for unknown overwrite semantics, absent/colliding child identities, invalidated host/cert/grant, attempted source deletion after partial/unverified Copy, journal replay after an uncertain write, a Sharesheet labeled saved-to-Drive, claimed bulk Rename Apply when disabled, or a synthetic-only route labeled physically accepted.
- Keep historical PR/run details in [RELEASE-READINESS.md](RELEASE-READINESS.md) and Git history. Keep [WORK-QUEUE.md](../../android-transfer/WORK-QUEUE.md) short and forward-looking; revise this plan only when architecture or dependency assumptions change.
