## Product identity and scope

Expository Transfer is a **native Android file-transfer application** using its own app identity and authorization. The existing Expository GitHub Pages repository browser is a different, strictly **read-only** application. Keep native code inside `android-transfer/` pending an explicitly approved repository migration. No relay service, shared web token, mandatory Expository account, global storage grant, telemetry containing filenames, or unrequested automatic sync.

**The product promise:** with authorized endpoints, make a truthful source → destination plan that a user can inspect and execute, then provide precise per-item outcomes without losing originals or silently repeating uncertain writes.

**2026-10-27 accepted incremental corrections (historical):** Merged #210 and #211 require fresh SFTP source-parent membership and explicit frozen Android-picker upload confirmation. Merged #213 makes *unencrypted, consented, read-only* FTP browsing available in Single and Dual, without FTP data transfer. Merged #214 binds FTPS Save As to its pre-picker file revision and retains TLS 1.2-only compatibility with certificate and hostname validation. Merged #215 introduced 1–12-file SFTP→SFTP Copy, backed by synthetic Android loopback byte proof #40613881485. These were incremental steps, not full P0 delivery.

**Current developer-preview implementation (29 October):** Default Single and optional independently navigable Dual workspaces can browse local/document-provider trees, pinned SFTP, verified encrypted FTPS, separately consented read-only FTP and anonymous public GitHub. User-picked Android file Save As, scoped New Folder and reviewed 1–12-file SAF/SFTP Copy routes exist; SFTP→SFTP handset relay has an actual synthetic Android byte-verification test. The app has scoped Local Open/Share, SFTP New Folder and limited one-file Move, verified-only journaled Copy receipts, an encrypted **connection-details-only** SFTP bookmark, and preview-only guarded bulk rename.

**New recursive SAF folder Copy:** [#275](https://github.com/gamesbyian/Expository/pull/275) implements a guarded per-step journaled Android DocumentsProvider destination executor with nested/empty folder creation and independent SHA-256 file readback. [#278](https://github.com/gamesbyian/Expository/pull/278) and [#282](https://github.com/gamesbyian/Expository/pull/282) expose explicit approval in Dual and Single respectively, with Single using the OS destination tree picker. [#284](https://github.com/gamesbyian/Expository/pull/284) and [#288](https://github.com/gamesbyian/Expository/pull/288) reject post-readback destination drift and displaced folder ancestry. [#286](https://github.com/gamesbyian/Expository/pull/286)/[#289](https://github.com/gamesbyian/Expository/pull/289) provide committed-step-only foreground progress. [Exact-head API35 E2 #40794689625](https://github.com/gamesbyian/Expository/actions/runs/40794689625) covers disposable synthetic provider bytes and progress. **The full system-picked, independently writable two-provider end-to-end folder journey is not yet accepted**, nor is a real Drive/cloud provider or hardware E4. Same-authority recursive overlap remains conservatively blocked.

**Still required for P0:** A unified fully featured Single endpoint experience; drag-to-propose parity; complete six-direction file and recursive folder routes including controlled FTPS data writes; bulk Rename Apply and safe Undo; a bounded persistent resume/reconciliation queue; actual verified Drive original-file upload and separate Docs conversion; biometric/session access gates; >2,000-child and large-stream stress, accessibility at large text sizes, real-device/provider E4 and independently signed E5 beta. Full requirement rows below remain binding: a working preview slice does not close a release gate. Consult the [evidence ledger](RELEASE-READINESS.md) before claiming completion.

**Additional binding authentication requirement:** optional Local and Remote access lock, configurable cadence (once per app session by default when enabled, return, idle or each protected operation), Android fingerprint/biometric and device credential where supported, profile-bound Keystore security for any saved remote credentials. This is a separate UI gate from the real protocol login and the Android file-provider permission. See [session authentication](SESSION-AUTHENTICATION.md). E1 policy exists before E2/E4 enforcement; do not call it delivered.

For cross-server Remote→Remote, data ordinarily flows through the handset, with honest metered-network/storage implications; **no FXP** default. Same-server **Copy** is not implemented with rename. The current developer preview uses progressive bounded listings through 2,000 rows and an upload picker batch limit of 12; these are **temporary implementation ceilings**, not P0 folder, browsing or workspace acceptance.

## Required operation matrix

| From → to | Copy | Explicit Move | Important distinction |
|---|---|---|---|
| Local SAF → Local SAF | Stream or verified provider-native copy | Prefer authorized provider-native move; else Copy→verify→user-confirmed delete | Different providers/grants possible; SAF rename/move may replace the URI |
| Local SAF → Remote | Phone-mediated scoped upload | Copy→verify→user-confirmed source delete when separately supported | Never infer source path from display name |
| Remote → Local SAF | Android Save As/tree creation and streaming | Copy→verify→user-confirmed remote delete only with explicit capability | Provider acknowledgement ≠ cloud synchronization |
| Remote → same verified server/namespace | Copy via supported safe server-copy or device relay | Verified SFTP rename / FTP RNFR–RNTO if capable, no overwrite | Rename is never the Copy optimization; no assumed atomicity |
| Remote A → Remote B (different account/server) | Explicit handset relay using both authenticated sessions | Copy→verify→user-confirmed source delete; may remain unsupported | Distinct authentication, session, path roots, metered costs |
| Local or Remote → Google Drive | Verified writable SAF provider or narrow `drive.file` API with identity/receipt | **Not in v1** | Share/open/Docs conversion are *different* actions |
| Local or Remote → Google Docs | Explicit supported-file conversion, or external Open | **Not in v1** | A Google Doc is not byte-identical to source |

**Every write:** immutable selected-item and target authority/version snapshot → show operation and conflict policy → require consent → revalidate just before mutation → journal before side effects → stream/commit → inspect destination → receipt. Unknown permission, path identity, symlink boundary, listing completeness or collision policy **blocks destructive paths**. Copy preserves source. Source deletion needs explicit separate consent and destination proof, not an unverified handoff, FTP acknowledgement, metadata coincidence or cloud icon.

**Crash/ambiguity:** `UNCERTAIN` is neither failure nor success. Never replay ambiguous FTP RNFR/RNTO, SFTP rename, staged commit, create/overwrite, Drive create or source delete until the actual endpoint has been reconciled. If identity cannot be established, present manual inspection and retain originals. No automatic cleanup of unknown remote temporary files. Journal and previews must not leak profile addresses, tokens, filenames or private contents to CI/telemetry.

## UX contract

- **Single-location is the default, fully featured, permanent user-selectable view**, not merely a responsive fallback or temporary entry screen. Browse and manage one local or remote location at a time; Save, Upload, New Folder, Move to, Copy to and Rename must work without opening dual-pane mode. The system picker and ordinary destination navigation support transfers to other locations while remaining in single view.
- **Dual-location is an optional view choice**, not a separate workflow or compulsory replacement. It has independently configurable A/B locations, two breadcrumbs and clear **Copy A→B / B→A** actions. Device↔Device, Device↔Server and Server↔Server presets are shortcuts, not restrictions. The user can enter or leave dual view explicitly at any supported screen size. Preserve each location's path, selection and scroll when switching views or swapping panes; never silently transfer or reinterpret a pending Move. No fake split constructed from Local/SFTP/FTPS tabs.
- At 360/393/412dp portrait, support accessible 48dp targets, insets, scrollable sheets and keyboard/IME. If the user has selected dual view and 200% font or small height makes simultaneous panes unusable, present **A/B tabs with persistent destination summary** as the responsive representation of dual view, preserving both navigation and selection states. **This automatic tab collapse must not change the user's selected single/dual preference.** Test landscape and foldable/tablet arrangements too.
- Dragging onto an existing folder or blank pane surface opens the **same** Copy preflight as the button; explicit Move remains separate. No drag-only commands or unexpected source change when swapping panels.
- Rename compact sheet keeps fixed counts/error summary, operation chips, sort/number preview, extension lock and always-accessible Apply/Cancel; virtualize without changing numerical order. Apply disabled until native path is fully proven; never label preview-only implementation beta-complete.
- Receipts name *what was verified*: `HANDED_OFF_UNVERIFIED`, `WRITE_ACKNOWLEDGED`, `DESTINATION_CONFIRMED`, `CONTENT_HASH_VERIFIED` (only with actual byte-equivalent readback), `GOOGLE_DOC_CREATED`, `UNCERTAIN`. “100% sent” never implies remote persistence/Drive cloud commit.

## Quality, consent and privacy

Use synthetic E1 and API 35 E2 frequently, controlled protocol E3 intentionally, physical device + actual authorized provider E4 for P0 claims, and independent E5 for release. CI passes are scoped to **exact SHA, test suite, platform, run, expected assertions and inspected result**. A run request or compiled APK does not prove execution. Do not place personal servers, credentials, private paths or real-account screenshots in public logs/artifacts. Live mutation requires explicit authorized disposable fixtures; do not probe or alter third-party demo data. Prefer JVM checks and focused PR-head Android tests to broad costly reruns. Separate defects in disposable DocumentsUI fixtures from app behavioral failures.

Performance/stress gates include >2GiB streams, 2,000-child/large directories, 10,000 preview rows, network stalls, nonseekable SAF content, low storage, resume token/session expiry, account switching and malformed/out-of-order Android Intents. Never infer provider support from an action name alone; test per-item capability and grant lifetime.

**Release is blocked** by silent overwrite/deletion; untrusted TLS or changed SSH key accepted; automatic unsafe downgrade/retry; wrong-source picker race; indefinite stalled I/O falsely marked complete; false Drive/Docs receipts; nonreconcilable staging; drag-only operations; off-screen controls at 200% font; incomplete six-direction/folder flows; missing E4/E5.
