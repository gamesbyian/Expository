## Delivery order and tightly coupled batches

1. **Immediate parallel foundation slices:** T1 extends the already accepted Single/Dual SAF command seam to a remote route; T2 adds exact-authority operator reconciliation and per-item durable queue; T3 probes FTPS/SFTP capability/real-byte routes; T5 verifies genuine Drive account + writable parent; T6 handles auth and Gradle integrity independently. One owner per overlapping production file; no universal refactor before a concrete route needs it.
2. **First integrated transfer slice:** one actual remotely authenticated file/folder Copy through T1 + T2 + T3, with one frozen approval, independent destination evidence, interruption receipt, stale permission/collision refusal and a Single/Dual entry-point parity check. Extend the route matrix incrementally, *not* as independent Copy engines.
3. **Integrate deletion-enabled Move in the same route work:** direct same-authority Move where supported, otherwise Copy→verify→delete under **one** explicit Move confirmation. Recheck exact original identity and delete capability just before deletion. Stop/report ambiguous writes/deletions, and never demand a second routine consent or unsupported checksum.
4. **Reuse the resulting executor:** connect T4 bulk Rename Apply and N-folder Smart Merge to the same lifecycle, preflight and recovery services. Keep their own cycle/collision and multi-source authority tests. Do not implement separate competing journals or destination state machines.
5. **Add cloud original-file support:** T5 builds genuine Drive uploads through that same authority/execution seam, with its separate OAuth/account, parent and upload-session proof. Native Docs conversion remains a semantically different action. Extended full Drive/GitHub browsing and torrent-awareness should not delay the initial scoped Drive destination proof.
6. **Continuous qualification, final release gate:** T6 and T7 run targeted security, accessibility and realistic performance checks as each changed route becomes testable; reserve final signed E5 for full contract completion. Do not postpone all device evidence until after all engineering, and do not mark G9 done because one Android emulator journey is green.

## Testing economy without diluted acceptance

- **Reuse a single setup** for compatible deterministic JVM classes, several independent synthetic provider paths and multiple related routes, where they can share fixtures without state contamination. Assert each route, direction, result type and failure phase distinctly even when run in one job.
- **Preserve isolation** for real two-picker journeys, process kill/relaunch, grant revocation, lost acknowledgements, network trust failures, hostile provider state and actual account/physical-device E4. Do not batch tests in ways that erase their independent authority or perturb timing.
- **Build a reusable failure matrix** for stale source/target identity, collision/no-replace, cancel, lost reply, partial data, process death, permission loss and exact subsequent reconciliation. Parameterize where equivalent; add specific tests for protocol semantics, native Move, rename swaps, Smart Merge overlapping inputs and Drive file/session identity.
- **Reuse evidence only for the same fact.** A byte-verified SAF Copy can qualify the common executor invariant for that scenario, but does not automatically qualify SFTP, FTPS, Drive, Rename, Move, N-folder Merge, TalkBack, physical phone or signed release. Keep per-route E2/E3, per-provider E4 and E5 ledger entries with exact SHA and observations.
- **Test proportionately.** Cheap E1 and compile gates on changed surfaces; one relevant installed or protocol gate when crossing those boundaries; no blind rerun of unchanged broad suites. Maintain explicit `NOT RUN` and `NOT VERIFIED` where evidence is absent.

## Owner/issue discipline and definition of finished

- **Keep existing issues open** until their entire acceptance contracts are met, including #324/#325/#28/#26/#27/#384/#25/#326/#327. Cross-referencing one feature's shared foundation is not closure. No duplicate tracker issues for a different audit sentence.
- **One shared implementation owner per slice.** A PR should name (a) the shared invariant improved, (b) which audit concerns and issue acceptance rows it advances, (c) the exact routes/operations exercised, (d) independent proofs still needed, and (e) the production file ownership and potential overlap with other PRs. Split PRs by independently verifiable behaviour, not by duplicate UI mode or a redundant evidence class.
- **Do not replace distinct semantics with generic guarantees.** Direct Move, copy-verify-delete, Copy, Rename Apply, N-source Smart Merge and Drive conversion have different result and recovery claims. All share the execution envelope only where their behaviours truly overlap.
- **No scope erasure:** preserve mandatory P01–P12 beta features, required safety refusal rules, accessibility and E4/E5 release gates. P13 Smart Merge and the optional Chunks/GitHub/cloud expansions retain their approved scope and priority outside the original P01–P12 beta unless separately reprioritized.
