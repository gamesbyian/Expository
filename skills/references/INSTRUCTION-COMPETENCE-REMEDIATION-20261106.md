# Instruction competence audit: remediation map (2026-11-06)

**Status:** editorial follow-up to the 149-file read-only audit at source commit e114ade9333424360e07b182c0215d28f70e5792. This report records the methods now proposed on the development branch and consequential gaps remaining. It is not an independent assessment of actual agent performance. No historical case study or evaluation campaign is triggered.

## Source and standards

The original 149-file corpus contained 69 Markdown documents, 59 Python files, 19 JSON files and two CSVs. Audited instructions span Project Inception, Android Development, Engineering Judgment, Mechanised Expertise, Concept Model Engineering, Human-Agent Interaction, Decision Synthesis and the capability router. Existing strong mechanisms include the nine inquiry operators, M1–M7 concept-map construction, validation economics, source-lineage checks, and authorization-aware choice handling.

An instruction is **mechanically complete in design** only when the agent can discover a method specifying its trigger, rejection, obtainable source inputs, transform, consequential branch, observable result, evidence/oracle, stopping condition and fallback. Passing static validation cannot prove the agent actually did or understood the work.

## Prioritization and limits

The highest-value procedural omissions for new-project work were evidence collection, reusable-resource research and product specification. They now have separate independently activatable skills with explicit execution/failure branches and worked negative cases. The Project Inception skill orchestrates these only when needed; Android, Engineering Judgment and Human-Agent Interaction route to them conditionally. Routine reversible work still rejects full inception research.

The instruction-quality tool deliberately reports **review candidates**, not false "all instructions complete" certification. Anchored contracts cover selected important instructions only; an actual semantic review must examine unhandled commands and linked procedures. Structural CI tests cannot establish the correctness of external research, an SDK license interpretation, full product completeness or agent proficiency.

A later authorized evaluation should include unfamiliar product ecosystems, unavailable sources, duplicate testimonials, incompatible open-source packages, missing preference authority, a speculative feature list, contradictory UI/data ownership and routine no-action controls. Inspect decisions and shipped outcomes independently; do not schedule agents solely because this plan exists.

## Portability

All new instructions and examples are located within skills/ and use local relative links. No external repo is needed to follow internal procedure instructions. Historical GitHub references are evidence, not executable prerequisites. Run the existing portability checker, anchored instruction tests and independent copied-project smoke before accepting migration into another repo.

**Acceptance to report:** exact source/head, files/paths changed, tests actually executed, sampled false-positive and false-negative auditor controls, remaining semantic uncertainties and whether the destination installed package matches the pinned canonical version.
